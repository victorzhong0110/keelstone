## 为什么不是 tc netem

宿主机和 Alpine 容器里都执行过：

```text
tc qdisc replace dev lo root netem delay 1ms
Error: Specified qdisc kind is unknown.
```

`sch_netem` 不在这颗内核里，模块也装不进去。`tbf` 有，但它只能限速，不能加延迟。

替代是三个 `--network none` 的容器，各自一对 veth，由宿主机上的 `cmd/l2delay` 做二层转发。每一帧按正态分布多等一段时间（标准差是 `-jitter`，负值截成 0），最后不到 300 µs 的等待会自旋。请求和响应各被 hold 一次，所以 ping 的 RTT 大约是单向延迟的两倍。校验和卸载关掉了，否则 AF_PACKET 转发的 TCP 校验和是空的，对端会丢。

这个交换机自己会占大约一个核。节点的 CPU 配额仍然由 cgroup 卡住，但宿主机一共只有 4 个 vCPU，还要跑 dockerd 和这个交换机。

## 拓扑和配额

三个节点加一个客户端，镜像 `keelstone-bench:local`（Alpine 3.20）。

| 容器 | 地址 | 限额 |
|---|---|---|
| keelstone-n1 | 10.10.0.11:43121 | `--cpus 0.5 --memory 256m --memory-swap 256m` |
| keelstone-n2 | 10.10.0.12:43121 | 同上 |
| keelstone-n3 | 10.10.0.13:43121 | 同上 |
| keelstone-client | 10.10.0.20 | `--cpus 1 --memory 512m --memory-swap 512m` |

两次负载（同机房 A、跨区 A）里，`keelstone-n1` 的 cgroup 都是：

```text
cpu.max=50000 100000
memory.max=268435456
```

`50000 100000` 是每个 100 ms 周期最多 50 ms，也就是 0.5 CPU。`268435456` 是 256 MiB。

节点参数：`--tick 20ms --election-tick 20 --heartbeat-tick 1 --snapshot-entries 8000`。选举超时是 20 到 39 个 tick，也就是 400–780 ms。每次提交都 fsync。

## 负载

YCSB 风格，不是官方 YCSB 进程：

- A：50% Get / 50% Put
- B：95% Get / 5% Put
- 键：Zipf，`s=0.99`，`v=1`，键空间 4096（`math/rand.Zipf`）
- 64 个闭合循环客户端
- 有读的负载先用最多 32 个 worker 把 4096 个键写满
- 预热 3 s 不计入，正式采样 12 s
- 单次操作上下文 3 s，单次 HTTP 尝试 2 s
- 错误是采样窗口里返回 error 的次数，不进入延迟分位
- 吞吐 = 成功次数 / 采样秒数

优化前的二进制是流水线改动之前编译的 `/tmp/keelstone-before`。它没有 `--max-inflight`，每个 follower 一次只飞一条 AppendEntries，节点间 HTTP 用默认的 `http.Client`（每个 host 只留 2 条空闲连接）。

优化后的二进制是当前的 `keelstone`：`--max-inflight 8`，节点间 HTTP 的空闲连接池是 `MaxIdleConns=128`、`MaxIdleConnsPerHost=64`。两边的客户端都是同一次编译的 `bench`，所以客户端连接池不是变量。

## 瓶颈

写混合（A）卡在单飞复制。优化前每个 follower 一个 RTT 里只能有一批 AppendEntries，64 个客户端都堆在这上面，每次提交还要 fsync，节点只有 0.5 CPU。跨区 n1→n2 的 ping 平均只有 4.699 ms，优化前写 P50 却是 45.550 ms、P99 143.321 ms，还在 12 秒里出了 115 个客户端超时。同机房同样的单飞是 62 个超时、写 P99 89.862 ms。窗口开到 8 之后这两次超时都变成 0，跨区 A 的吞吐变成 3.18 倍，因为 RTT 更长，重叠在途消息的收益更大。写 P99 仍然有几十毫秒，fsync 和 CPU 配额还在。

读混合（B）不是同一处。同机房 95% 是 ReadIndex，开窗口之后吞吐从 10876.10 降到 8683.77，总 P99 从 48.102 到 47.083，几乎没动，读 P50 从 3.216 变到 4.518。多出来的复制消息占用了本来就只有半个核的 leader。跨区 B 的那 5% 写仍被 RTT 拉长，窗口把写 P99 从 86.789 ms 降到 18.481 ms，总 P99 从 46.681 ms 降到 17.475 ms，吞吐变成 1.12 倍。

所以：延迟比 fsync 显眼时，先开复制窗口；读已经占绝大多数、RTT 又很小的时候，窗口不是下一步。

## 负载中的 Leader 故障转移

优化后的三节点，后台先跑 YCSB A（64 客户端，预热 1 s，时长 25 s）。探针单独一个客户端，尝试上限 150 ms。它往 stderr 打出 `READY` 之后，宿主机执行 `docker kill -s KILL`。计时从这条 kill 的墙上时钟，到新 leader 上第一次 `Put` 返回。写仍落在旧 leader 上不算完成。

六次退出码都是 137。

| 剖面 | 旧 leader | 新 leader | 毫秒 |
|---|---|---|---:|
| 同机房 | n1 | n3 | 1040.818243 |
| 同机房 | n3 | n2 | 1049.482114 |
| 同机房 | n3 | n1 | 1677.334452 |
| 跨区 | n1 | n2 | 1708.987911 |
| 跨区 | n3 | n1 | 1727.448593 |
| 跨区 | n1 | n2 | 824.514509 |

同机房 1040.818–1677.334 ms，跨区 824.515–1727.449 ms。选举超时本身是 400–780 ms。多出来的时间包括：0.5 CPU 上 tick 被负载拖慢、探针可能先打在已经死掉的连接上（最多 150 ms）再换节点、新 leader 还要提交一条 noop。跨区并没有系统性更慢，因为选举定时器比 4.7 ms 的 RTT 大得多。

另有一次同机房探针把尝试上限留在和负载一样的 2 s：旧 leader n2，新 leader n3，退出码 137，`failover_ms` 2047.318651。那一次几乎整段都耗在死连接的尝试预算上，不能当成选举时间。上面六次把探针改成 150 ms 就是为了避开这个。

## 线性一致性

复制窗口落地之后重跑，和 `docs/benchmark.md` 里 33.58 s 的那 20 轮不是同一次。

```bash
KEELSTONE_FAULT_ITERS=20 go test -count=1 -timeout 15m -run TestFaultLinearizable ./internal/cluster/ -v
```

2026-09-28T08:23:57Z 开始，08:24:30Z 结束。日志最后两行：

```text
fault_passed=20 fault_total=20
--- PASS: TestFaultLinearizable (32.60s)
ok  	github.com/victorzhong0110/keelstone/internal/cluster	32.612s
```

20 轮全部通过。每一轮是 3 节点、3 客户端、约 1.5 秒随机故障（分区、15%–35% 丢包、延迟、乱序、最多同时崩溃 1 个节点），然后恢复、重启、等状态机一致，再用 Porcupine 按 key 检查。这轮没有和容器压测叠在一起跑。

同一套代码上 `go test -race -count=1 -timeout 20m ./...` 在 2026-09-28T08:27:04Z 到 08:27:10Z 通过，里面包含默认的 3 轮故障注入。

## 怎么重跑

```bash
# 优化前的二进制要事先放到 /tmp/keelstone-before
CLIENTS=64 scripts/bench-realistic.sh
```

脚本会重建镜像、拆掉容器和 veth，并覆盖 `bench-data/realistic/results.jsonl`。`APPEND_RESULTS=1` 才追加。`ONLY_PROFILE=same-dc` 或 `cross-zone`，`SKIP_LOAD=1` 只测故障转移，`FAILOVER_SAMPLES` 控制次数。原始 JSON 在本机的 `bench-data/realistic/`，这个目录不进 git。
